Summary verdict

MERGE-AFTER-FIX — the routing constants and pool definition are correct, but the cdp:tv seed INSERT was appended inside the if current_version < 5: migration guard, so it never executes on the existing production database already at schema version 5 — the PR is a no-op on the only durable database it exists to repair.

SHIP-BLOCKING findings

SB-1 — The cdp:tv pool row is unreachable on an already-migrated database (Q1). Per §7.2, all pool seeding lives inside _init_db under if current_version < 5:, and _init_db runs on every ConductorStore.__init__ (line 1026). The production workstation's schema_migrations table already recorded version 5 when #90 merged, so on every store construction after this PR deploys, current_version < 5 evaluates False and the entire block — including this PR's new INSERT OR IGNORE ... VALUES ('cdp:tv', 1, 1, ...) at the marked insertion point — is skipped. This PR does not bump the schema version and adds no current_version < 6 block, so no code path ever inserts the row into a v5 database. Only fresh databases (no schema_migrations rows, current_version effectively 0) execute the seed. The PR's sole purpose — giving CCTV a pool — therefore does not land in production.

Minimal correct fix: move the cdp:tv INSERT OR IGNORE out of the < 5 block into a new if current_version < 6: block that also runs INSERT OR IGNORE INTO schema_migrations (version, applied_at_utc) VALUES (6, datetime('now')). Fresh databases execute both blocks and still get the row; v5 databases execute only the new block. Structurally better (and worth one sentence in the PR discussion): pool seeding is idempotent by construction (INSERT OR IGNORE), so hoisting it out of the version guard entirely would make this class of defect impossible for every future pool. Either fix must be accompanied by the upgrade-path test named in Q2, since the current suite structurally cannot see this defect.

No test asserts resolve_resource_key(purpose="cdp_tv") == "cdp:tv", that purpose="cdp_tv" passes VALID_PURPOSES validation, or that purpose="cdp_tv" is refused on host:heavy under #90's enforcement.

The PR is delta-neutral on the constant but the new test enshrines purpose="cdp_provider" + explicit resource_key as CCTV's admission shape, entrenching the legacy purpose instead of migrating to purpose="cdp_tv" / role="chrome_tv".

FL-3 (Q5): A capacity-1 pool with DEFAULT_LEASE_TTL_SECONDS = 300 fencing is only sound for the continuous chrome_tv lane if a lease-renewal/heartbeat path exists and CCTV uses it; otherwise a healthy lane is fenced every 300 s. The renewal API is not in §7 — verify before the consumer adoption lands.

Answers to the six questions
Q1 — Migration reachability

No, the row is not seeded on an existing v5 database. Trace: _init_db runs on every construction; current_version is 5 on the production DB (migration 5 applied at #90 merge, per §7.2); if current_version < 5: is False; the block containing the new INSERT OR IGNORE ... 'cdp:tv' is skipped; no < 6 block or version bump exists; no other supplied code inserts pool rows. The seed fires only on databases below version 5 — i.e., fresh ones.

On what CCTV observes at runtime once its adoption lands with resource_key="cdp:tv" against a row-less database: the HostResourceManager.request body is not supplied, so the exact behavior is unverifiable, and I state the assumption explicitly. The fail-closed reading is most consistent with the visible design — admission consults persisted per-pool state (the enabled column, per test_per_pool_disable_isolates_only_disabled_pool), ResourceAdmissionError exists, and #90 built refusal machinery — i.e., an unknown resource_key is refused, and CCTV hard-fails exactly as the new test's own docstring predicts for an un-pooled lane. The alternative is a silent fallback to DEFAULT_POOL_CAPACITIES["cdp:tv"], which would admit off-book with unpersisted policy (disable/status readback broken). Admit-unbounded has no supporting symbol in §7. All three outcomes fail the PR's intent; the fix is the migration-6 block (or hoisted idempotent seeding) above.

Q2 — Test blindness

Every test constructs ConductorStore(root_dir=tmp_path): an empty database with no schema_migrations rows, so current_version is 0, every version guard is True, and the seed block always runs. The suite only ever exercises the guard's True branch; the production branch (current_version == 5, guard False) is never instantiated, so SB-1 is invisible to it. The test that would catch it is an upgrade-path test, e.g. test_cdp_tv_pool_seeded_when_opening_existing_v5_database: arrange a database at the pre-PR state (four pool rows, schema_migrations containing version 5, no cdp:tv), construct ConductorStore on that same root with the head code, then assert the cdp:tv row exists and HostResourceManager(store, resource_key="cdp:tv").request(...) returns ACTIVE. On the current diff that test fails at the row-existence assertion.

Q3 — Purpose vs role coverage

The role path is covered: test_chrome_tv_role_routes_to_cdp_tv asserts resolve_resource_key(role="chrome_tv") == "cdp:tv". The purpose path is not exercised anywhere in the diff: test_cdp_tv_pool_admits_cctv_and_isolates_from_host_heavy passes purpose="cdp_provider" with the manager constructed on explicit resource_key="cdp:tv", and per resolve_resource_key in §7.3 the explicit resource_key wins before purpose is consulted — the cdp_tv entry in PURPOSE_TO_RESOURCE_KEY and its VALID_PURPOSES membership could both be deleted and this suite would stay green. On #90's cdp_*-refused-on-host:heavy enforcement: the refusal predicate is not in §7, so coverage is unverifiable. If it is a cdp_ prefix match or a PURPOSE_TO_RESOURCE_KEY/CDP_POOLS membership check, cdp_tv is covered automatically because this PR updated both constants consistently; if it is a hard-coded purpose list written in #90, it predates cdp_tv and does not cover it. Either way, no test proves purpose="cdp_tv" is refused on host:heavy — add one mirroring #90's enforcement tests.

Q4 — cdp_provider fallthrough

cdp_provider is a legacy generic purpose from before #90's per-provider split: valid, but absent from PURPOSE_TO_RESOURCE_KEY, so resolve_resource_key(purpose="cdp_provider") returns "host:heavy" — where, under #90's enforcement (assuming the prefix/mapping predicate), a cdp_* purpose is refused. It is a trap: passes validation, guaranteed-refused at admission for any caller that does not also pass an explicit resource_key. It cannot be mapped to a single pool post-split, since "some provider" is exactly what #90 eliminated. This PR leaves the constant untouched — treating base behavior as fixed, that is delta-neutral — but it makes the situation mildly worse by writing the trap into the new test as CCTV's admission shape, normalized by the explicit-key override. Fix-later: deprecate cdp_provider (or alias with a warning) once consumers migrate, and have the CCTV adoption use role="chrome_tv" or purpose="cdp_tv", which also closes the FL-1 coverage gap.

Q5 — Capacity 1 for a continuous lane

Capacity 1 is the right shape for this lane; the TTL semantics are the risk. chrome_tv is a dedicated browser on a dedicated TV profile (port 9225, not fleet-shared), so singleton admission is precisely the desired invariant — two drivers on one capture browser is the real hazard, and there is no cross-lane starvation to recreate because CCTV is the lane's only consumer. The demonstrated hazard is liveness: with DEFAULT_LEASE_TTL_SECONDS = 300, the new test itself shows reconcile at TTL+60 producing recovery_required == 1, i.e., any holder that does not renew is fenced, healthy or not. The model is therefore sound only if a lease-renewal/heartbeat path exists and CCTV heartbeats; that API is not in §7 and is unverified. If it does not exist, the PR recreates the problem one level down — a healthy continuous lane fenced every 300 s, with the re-admission behavior of a RECOVERY_REQUIRED pool itself not shown. This is not a merge blocker (the hazard is latent until the consumer adoption lands) but is a documented precondition for it. The isolation assertions in the same test do confirm a cdp:tv fence does not disturb host:heavy or cdp:perplexity, which is the correct behavior.

Q6 — DEFAULT_RESOURCE_POOLS consumers

The visible consumer is read_all_pools_live, defined immediately below the tuple in scripts/conductor_store.py — it presumably iterates the constant, so status readback widens from four pools to five. That is additive and safe for tolerant renderers on any database where the row exists. The sharp edge is the window before SB-1's fix reaches production: the constant says five pools while the v5 database holds four rows, so any consumer that joins the constant against host_resource_pools will hit a missing cdp:tv row — a doctor check would (correctly, but newly) alarm, and a snapshot reader might synthesize zeros or error; those bodies are not supplied, so the degradation mode is unverified. The Conductor GUI and doctor modules are likewise not supplied; a hard-coded four-panel layout or an exact-set assertion would break, a data-driven one will not — flagged as unverified, not asserted. DEFAULT_POOL_CAPACITIES gained cdp:tv consistently, so capacity-fallback consumers stay coherent.
