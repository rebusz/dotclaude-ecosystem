# Audit — ByteDance Seed 1.6

Model: `bytedance-seed/seed-1.6`  
Tokens: 16,575  
Latency: 61.2s

---

### Audit Findings

#### 1. Architectural Soundness
- **Finding 1: Unclear ownership of operator token authorization for CU0-L**  
  Cited section: ## Implementation Tasks > CU0-L (P1, live contract capture)  
  The plan requires the literal operator token `GO CURSOR CU0-L LIVE CONTRACT CAPTURE` for CU0-L authorization but does not define: (a) who owns token distribution, (b) how to validate token usage post-probe, or (c) what happens if the token is misused. This blocks progress on CU0-L, a mandatory gate for Cursor implementation.  
  Grade: P1 (blocker)
- **Finding 2: Unresolved responsibility for projection error escalation**  
  Cited section: ## Architecture  
  The Codex rollout JSONL projection feeds into existing transcript readers, but the plan does not explicitly define how projection errors (e.g., malformed records) are escalated between `transcript_projection.py` and its consumers (Curator, lifecycle scripts). This creates ambiguity about who logs/remediates cross-boundary errors.  
  Grade: P2 (important)

#### 2. Threading/Async Safety
- **Finding 3: Blocking I/O risk on hot paths for high-volume sessions**  
  Cited section: ## Implementation slices > C3 — Global hook template and activation  
  Codex runs command hooks as a synchronous process per event. The plan acknowledges 10x/100x session volume pressure but does not outline async alternatives (e.g., process pooling) or load-throttling for hot paths. This could lead to timeout cascades during peak session activity.  
  Grade: P2 (important)
- **Finding 4: Untested concurrent registry write lock contention**  
  Cited section: ## Repository registry scope  
  The shared registry expansion is validated for single-session use but not for concurrent Codex/Claude sessions writing to the same registry. Existing session-ID namespacing does not address lock contention on shared registry root entries.  
  Grade: P3 (nice-to-have)

#### 3. Edge Cases
- **Finding 5: Unhandled nonce delay degraded mode gap**  
  Cited section: ## Definition of done — Cursor slice + ## Cursor discovery evidence  
  The Cursor slice requires nonce verification for context injection, but the plan does not address nonce loss due to host hook activation delays (e.g., IDE startup lag) rather than non-activation. This leads to false negatives for degraded mode classification.  
  Grade: P1 (blocker)
- **Finding 6: Uncovered Windows path normalization failure**  
  Cited section: ## Failure map and rollback + ## Repository registry scope  
  The plan mandates Windows path normalization but does not include a failure case for mixed forward/back slash conflicts in registry roots. This could lead to unregistered repositories despite valid paths.  
  Grade: P2 (important)

#### 4. Cost/Performance
- **Finding 7: Unidentified latency root cause for Codex slice**  
  Cited section: ## Codex closeout evidence — 2026-07-27  
  Codex’s p95 latency (565ms start, 777ms end) exceeds aspirational targets, but the plan does not specify if latency stems from adapter overhead or existing lifecycle scripts. Without root-cause identification, 10x/100x volume could hit hard timeouts.  
  Grade: P2 (important)
- **Finding 8: Redundant installer preflight subprocess calls**  
  Cited section: ## Implementation slices > C3 — Global hook template and activation  
  The installer runs `codex --version` on every activation without caching the result, leading to redundant subprocess calls on repeated installs.  
  Grade: P3 (nice-to-have)

#### 5. Integration Risks
- **Finding 9: Stale Claude state conflict in expanded registry roots**  
  Cited section: ## Repository registry scope  
  The plan expands the shared registry to 10 new Git roots but does not verify if these roots have existing stale Claude state (e.g., orphaned bindings). This could lead to mismatched verdicts between new Codex sessions and legacy Claude state.  
  Grade: P1 (blocker)
- **Finding 10: Unaddressed Cursor `conversation_id` collision risk**  
  Cited section: ## Cursor adapter boundary and delivery slices  
  The plan relies on Cursor’s documented `conversation_id` stability but does not address potential ID collisions across IDE/CLI surfaces (e.g., duplicate UUIDs for separate sessions).  
  Grade: P2 (important)

#### 6. Underspecified Areas
- **Finding 11: Undefined nonce format/validation for CU0-L**  
  Cited section: ## Implementation Tasks > CU0-L (P1, live contract capture)  
  The plan requires capturing a "nonce result" for Cursor context validation but does not define: (a) the nonce’s structure, (b) how it’s injected into the probe, or (c) how to validate it without transcript contents. This makes CU0-L unimplementable as written.  
  Grade: P1 (blocker)
- **Finding 12: Undefined "cold"/"warm" subprocess metrics**  
  Cited section: ## Performance review — 2 measured gates  
  The plan mandates measuring cold/warm p50/p95 latency but does not define thresholds for cold (e.g., first run post-reboot) vs warm (e.g., subsequent runs within 5 minutes) invocations.  
  Grade: P2 (important)

### TOP 3 CHANGES
1. **Define operator token ownership and validation for CU0-L** (P1, ## Implementation Tasks > CU0-L): Add explicit rules for token distribution (e.g., `dotclaude-ecosystem` team only), post-probe token revocation, and audit logging of token usage to unblock CU0-L activation.
2. **Address stale Claude state conflicts in expanded registry roots** (P1, ## Repository registry scope): Add a pre-activation step to scan new registry roots for stale Claude state (orphaned bindings, outdated verdicts) and mark them for reaper cleanup before Codex/Claude session access.
3. **Specify nonce format and validation for Cursor CU0-L** (P1, ## Implementation Tasks > CU0-L): Define a nonce structure (e.g., SHA-256 hash of probe workspace root + timestamp), injection method (probe-owned temporary hook config), and validation logic (match nonce in probe output against injected value) to enable context injection verification without transcript contents.
